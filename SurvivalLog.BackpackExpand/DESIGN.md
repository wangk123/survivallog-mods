# 背包扩容 BackpackExpand — 设计文档

> 本文档随源码存放在 mod 自己的文件夹内；**每次迭代改动必须同步更新本文档**（文档维护规则见 `docs\00-目录说明.md`）。
> 版本：跟随套件 version.json；机制与实证结论长期有效。

## 1. 功能定位

把可穿戴背包的格子容量和负重上限放大（默认宽、高各 ×1.5 ≈ 2.2 倍面积，负重 ×2），覆盖全部可获得背包（普通/登山包链、仓管背包链）。不改存档、不改游戏文件，删 dll 即还原。

## 2. 实现原理（原生机制实证，反汇编 + 运行时 dump）

- 改写对象是**内存配置表** `ConfigManager._Config_Bag_Dict`（键 = BagId）。
  `Config_Bag.Size` 为 `List<int>`，`[0]=宽 [1]=高`；游戏逻辑层、天赋层、UI reducer **三层实时直读该表，无快照**——所以改完立刻反映到背包界面。
- `Config_Bag.Burden`（负重）不同：它是 `BagComponent.OnInit / SetBagConfigId` 时的**快照**，改表后需要**重新读档**才体现到玩家身上。
- 负重上限公式（GetMaxBurden 反汇编实证）：
  `Round((Burden + ExtraBurden) × (1 + 天赋比例) + 天赋固定值)`
  即 mod 放大的基础值与天赋加成**独立叠加**，天赋收益不被吞。
- 天赋换包链（SurvivalPlanningComponent.BagGridBagIdsByInitialBag 静态实证）：
  普通背包 `1→[5,6,7]`、仓管 `8→[9,10,11]`。换包逻辑要求"链上新包尺寸 ≥ 当前包"才生效，
  因此 mod **整链统一改写**（链内相对大小关系保持）→ 天赋换包/升级照常工作。
- 改完 Size 后需要把 `ConfigManager._bagSizeSet` 置 null（尺寸白名单懒重建，见共享源码），
  下一次 HasBagSize 检查会按改写后的表重建。

## 3. 代码结构

| 文件 | 职责 |
|---|---|
| `BackpackExpandPlugin.cs` | 入口：配置定义（Config.Bind）、配置变更→Rerun、注入 Ticker |
| `BackpackTicker`（同文件） | MonoBehaviour 每 5 秒轮询幂等改写；首单公告 |
| `ModShared\BagTableRw.cs` | 共享源码（编译进本 dll）：表访问、原值记忆、幂等改写（见 `ModShared\README.md`） |

### 为什么用"持续轮询 + 幂等"而不是一次性改写

配置表在切场景/读档时可能整体重载（对象重建、数值回原值），一次式改写会被覆盖。
轮询每 5 秒按 `原值 × 倍数` 重写一遍：任何时刻被游戏重置，最多 5 秒内自动恢复。
幂等由共享层的"进程内原值字典"保证（首次读到的值记为原值，永远以原值为基准计算）。

## 4. 配置项（BepInEx\config\com.local.survivallog.backpackexpand.cfg）

| 键 | 默认 | 说明 |
|---|---|---|
| WidthMult | 1.5 | 宽度倍数（AwayFromZero 四舍五入，7×1.5=10.5→11）。宽高同乘避免单边过长被 UI 压缩 |
| HeightMult | 1.5 | 高度倍数（同上） |
| BurdenMult | 2 | 负重倍数，仅背包基础值；天赋加成不受影响。**改后需重新读档** |
| ExtraIds | 空 | 追加 BagId（逗号分隔） |
| ExcludeIds | 空 | 排除 BagId，优先级最高 |
| Verbose | false | 输出每条明细（含未变化项） |

所有倍数/名单项改动即时触发 Rerun（SettingChanged），无需重启游戏；仅负重因快照机制需读档。

## 5. 默认名单与依据

`DefaultIds = { 1, 2, 5, 6, 7, 8, 9, 10, 11 }`

- 1,2 = 初始普通背包链头；5,6,7 = 登山包天赋链；8,9,10,11 = 仓管背包天赋链（整链覆盖，见 §2）。
- 参考原值：普通链负重 9600、仓管链 12480、登山包 12000。
- **刻意不含**：购物车 3 / 轿车 4（本 mod 定位"背包"，且容量巨大无需扩）。

## 6. 与原生 / 其他 mod 的交互

- 天赋（换包链、负重比例/固定加成）：全部照常，见 §2 公式与整链改写策略。
- 与 CabinetExpand / FridgeExpand 名单互不重叠（各自管理自己的 BagId），可任意组合安装。
- 不写任何存档字段、不碰 Data_Item；卸载后配置表随进程回收，游戏回到原版。

## 7. 已知限制

- 负重改表后需重新读档（快照机制，无法绕过）。
- 老存档里已穿上的背包：格子立即变大（直读），负重要读一次档。
