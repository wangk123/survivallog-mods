# 版本历史

## v2.9.29（2026-09-16）
- 【修复】拆分卡顿（工作台界面连续 Shift+左键拆分尤其严重）：
  - 【根因实证】（Il2CppDumper + Iced + 全 .text call 扫描）：
    1) 增量通知不是廉价操作——LogicAdapter.AddOrNotifyItem → RA_AddOrNotify 内部
       无条件调 UpdateBag → GetItemDataList（整包列表重建）+ Ac_BackpackUI_RefreshBag
       （整视图推送）。游戏自己每个数据变化只发一条所以流畅；mod 把它当增量刷子
       循环用，每条都是一次整视图推送。
    2) JS 侧（webui-bag.js createGridBag / ToolTable.html）收到 BagMsg 后
       initGrid/renderItems 无 diff 全量重建 DOM（清 innerHTML + 重建全部物品元素）。
    3) 旧拆分路径 = NotifyUpsert(2条) + FullSyncOwner(容器N条) + 0.3s 补推(又N条)
       + QueueWebUiBagRefresh 三件套×2（OnSyncBagItems + RefreshAllBagViews×2
       + Cooking_RefreshBag）≈ 数十次整包 DOM 重建/次，连续拆分雪崩。
  - 【关键事实】增量链只推 BackpackUI 页面：Ac_ToolTable_RefreshBag /
    Ac_Cooking_RefreshBag 的调用方（全 call 扫描）只有各自 reducer 和
    RA_RefreshAllBagViews——即 v2.7.4"增量对柜子/工作台不可靠"的观察是对的，
    但当时的对策（全量循环 + 多轮补推）走错了方向：全量循环与增量同机制
    （一样只推 BackpackUI），真正起作用的只有三件套里的 RefreshAllBagViews。
  - 【修复】拆分成功后只做：NotifyUpsert(src, 新堆) 数据增量 + 一次官方
    Ac_Item_RefreshAllBagViews.SendAction()（无参，内部自判各界面开关并统一派发
    BackpackUI/ToolTable/Cooking 三路刷新）。其余全删。一次拆分从数十次整包
    DOM 重建降到背包页 2 次增量推送 + 全开界面各 1 次刷新，与官方捡物品等价。
  - 合并/整理路径本次不动（用户节奏操作，非连发场景）
- 【教训】"全量兜底"在推送型 UI 同步上是性能炸弹：推送成本不在调用侧而在
  渲染侧（JS 全量重建），N 条"增量"就是 N 次全量渲染。找对官方总闸动作
  （自判开关的 RefreshAllBagViews）一个顶全套。
