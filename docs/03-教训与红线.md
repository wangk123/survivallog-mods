# 教训与事故记录（红线清单）

> 每一条都是实际发生、有日志/存档实锤的事故。改代码前必读。

## 🔴 红线（违反 = 存档损坏/游戏崩溃/物品丢失，全部发生过）

1. **绝不克隆物品对象**（v2.8.0 事故）
   il2cpp_object_new + 字段复制出来的对象没跑游戏构造函数、没注册事件系统，
   原生 RemoveItem/整理/配方校验管线一碰就崩。

2. **绝不"置零源堆再恢复"**（v2.8.1 事故：纸片 18→1 真实丢失）
   SetItemCount(src,0) 后游戏管线立刻把该堆注销，恢复写入的是孤儿对象。

3. **绝不在反应层（Redux Reducer）改校验结果**（v2.8.7/v2.8.8 两次全游戏冻结）
   反应式状态机要求结果收敛；按帧窗口改返回值 → 非收敛 → 无限重渲染 → 主线程饱和。
   State/Reducer/Selector 一律不碰。

4. **绝不用第三方容器做拆分中转**（v2.9.0-v2.9.8 五次事故的总根源）
   OwnerCache 混有地面掉落等虚拟 owner，无法可靠区分真容器：
   - AddItem 写入虚拟容器 → 回滚 RemoveItem 留 count=0 残骸 →
   - 游戏脏检测器（GetItemDataList）LogError 洪水 → 错误反馈弹窗 → 无法操作
   - 残骸写回存档，每次"读档→回菜单→读档"**翻倍**（4184→8373 实锤）
   - 拆分失败的实物掉落散布全地图（用户看到的"垃圾山"）
   唯一安全方案 = SplitInPlace（单容器内压上限新建，见技术设计）。

5. **绝不只置零不删除**（v2.9.13 事故：48 条 x0 铁丝残骸，用户删档重开）
   合并的"安全合并"只 SetItemCount(dup,0)+删UI格 → 数据条目还在容器列表 →
   写回存档持续污染。必须 RemoveItem + OwnerCache 补删 + 验证。

6. **绝不写存档清洗/自动修复逻辑**（用户明确要求全部删除，v2.9.15）
   清理逻辑一旦有误判 = 误删玩家物品。宁可让用户删档重开，不做自动清档。

7. **绝不改 get/set_StackLimit 属性**（v2.7.1 之前：卡楼梯 bug）
   游戏启动时经非内联 getter 全表扫描（t=7.1s），补丁返回值污染派生数据 →
   寻路损坏。只允许对"容器中实际存在的物品"的配置做字段直写。

8. **绝不改写"多次使用物品"的 Config_Item.StackLimit**（v2.9.16 及之前：烹饪整份消耗）
   反汇编实锤（v2.9.19）：TryPreSplitForCooking 读 Config_Item.StackLimit（偏移 0x5C）
   要求 ≤1 才会 SplitItem(源,1) 预拆分"1 次使用"进烹饪区；>1 返回源自身 →
   整实例（全部使用次数）进烹饪区被整份消耗（野兔/胡萝卜/大米全中）。
   判定标准 = `ItemData.MaxUseTimes > 1`（总次数上限，不是剩余次数）；
   单次使用物品（上限=1）不受影响。改写范围必须排除这类配置。

## 🟡 规则（防止浪费时间的流程教训）

8. **部署前必须关游戏**：运行中 plugins DLL 被锁，Copy-Item 报错；
   曾因部署静默失败debug了半小时"为什么改动不生效"。
9. **HandleCallback 回调内禁止改游戏数据**：JS 桥重入 → 冻死。
   一律登记（_pending* 字段），ticker 主线程下一帧执行。
10. **Unity Input.GetKeyDown 收不到部分键盘输入**：拆分键轮询用 Win32
    GetAsyncKeyState（VK 字母=大写 ASCII，Unity=小写，要转换）。
11. **PowerShell 5.1 中文编码坑**：.ps1 存成 UTF-8 无 BOM 会被当 ANSI 解析 →
    乱码/解析错误。脚本一律 ASCII-only；中文文件名用 [char]0xXXXX 拼接。
12. **Edit 工具整块替换会吃掉相邻文档注释**：删块后必须检查上下文完整性。
13. **游戏 UI 自动化测试极不可靠**：视觉识别坐标漂移、WebView 点击穿透、
    Dpi 缩放（raster×2）、前台窗口被抢……能读日志推断的绝不开游戏实测；
    确需 UI 操作时用真实输入（SetForegroundWindow+mouse_event），raster 坐标 ×2。
14. **工具输出可能串扰/截断**：多命令管道长输出时出现过假日志行。
    重要结论必须用独立、小批量的查询复核。
15. **BepInEx 日志 UTF8、Player.log 在 %USERPROFILE%\AppData\LocalLow\LLS\SLGame**：
    崩溃/报错弹窗的真因通常只在 Player.log（游戏侧 LogError + 上报栈）。

## 环境事故（非 mod 代码缺陷，2026-10-24 xmod 卸载拆链）

**现象**：作者报"mod 全部失效"。日志停在最后一次正常会话（10:35，全 mod 加载成功），
其后启动无任何新日志——BepInEx 链根本没加载。

**证据链（文件时间戳 + 日志）**：

| 时间 | 事件 |
|---|---|
| 10:35 | 最后正常会话：全部 mod 加载与自证正常（含 RoleUnlock 互通、PlanPick 巡检打点） |
| 10:21→10:36 | xmod 安装/卸载动作：`dotnet\`、`BepInEx\core`、`BepInEx\unity-libs` 时间戳全部落在 xmod 操作窗口 |
| 事后现场 | 根目录 `winhttp.dll`（Doorstop 入口）与 `doorstop_config.ini` **被删**；`BepInEx\core` 只剩空 `runtimes`；`dotnet\` 清空；`unity-libs` 只剩 xmod 留下的 `6000.2.7.zip`；`plugins\xmod\` 只剩 AssetBundle/locales 空壳 |

**损害范围**：仅注入链三件套（winhttp/doorstop、dotnet 运行时、BepInEx core）。
plugins 全部 dll（含 PlanPick）、interop、cache、config、游戏存档 **全部完好**。
风灵月影（外部内存修改器）不装文件，与本次无关。

**根因**：xmod 的卸载流程破坏性清理了它认定"自己装过"的注入链文件——
而那条链是我们套件的（同用 BepInEx 生态，文件名/路径重叠），属于第三方工具卸载器误伤。

**恢复方案（已验证，10:4x 完成）**：

1. 重跑套件安装器 `release/生存日志MOD安装器_v1.3.8.exe`（图形界面点装；
   记忆坑：勿用 /SILENT，NextButtonClick 有静默挂死史）——重装 winhttp + dotnet + BepInEx core + 全套 mod；
   安装器名单外的 dll（如 PlanPick）已在 plugins，不受影响。
2. 装完**验三件套**：根目录 `winhttp.dll` + `doorstop_config.ini` 存在；`dotnet\` 有运行时 dll；
   `BepInEx\core` 有 BepInEx.Core.dll 等。
3. 启动游戏看 LogOutput.log 出现 Chainloader + 各 mod 自证行 = 恢复。

**预防（已入 AGENTS.md 硬规则 13）**：任何外部工具（xmod/修改器/loader）安装或卸载后，
先验三件套再启动游戏；被拆即重跑安装器。xmod 想再用：装完必须复查三件套。
