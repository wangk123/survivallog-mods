## 拆分原语（v2.9.10 SplitInPlace，当前唯一实现）

**单容器、零中转、零外部写入：**

1. 空格预检（TryResolveBagPos → FindFreeCell 兜底），无空格则安全退出
2. 临时把该物品配置的 `StackLimit` **写为 1**（Marshal 直写字段偏移）
   → 游戏眼中原版所有堆（count≥1）都"已满"
3. `AddItem(同一容器, cfg, 1, …)` → 必然不并堆、自动找空格新建 x1
4. `finally` 恢复原 StackLimit（999）——同一帧内完成，无窗口期
5. 多件拆分：`IncreaseItemCount(新堆, splitCount-1)`（原生 API，不会并错堆）
6. `SetItemCount(源堆, before-splitCount)`（永不为 0）
7. 补保质期字段（TimeLeft 四件套从源堆拷贝）
8. UI：NotifyUpsert + FullSyncOwner + 300ms 补推

失败路径：created 校验不过 → RemoveItem 回滚（原生对象安全）→ 物品无损。

## 关键游戏 API 事实（interop 反汇编/实测确证）

| API | 事实 |
|---|---|
| `SplitItem(instanceId, count)` | **可用，但有前提**（v2.9.19 反汇编确证）：仅当该物品 `Config_Item.StackLimit ≤ 1` 时执行；旧记录"恒返回 null"是 mod 把 StackLimit 改成 999 所致 |
| `TryPreSplitForCooking(itemId, ownerId)` | 官方烹饪预拆分入口：读 `Config_Item.StackLimit`（字段偏移 0x5C）要求 ≤1，通过则 `SplitItem(源,1)` 拆出 1 份并返回新份 InstanceId；>1 返回源自身（= 整实例进烹饪区、整份消耗）。**因此多次使用物品（MaxUseTimes>1）禁止改写 StackLimit** |
| `OnCookingQuickMove(itemId, from, to)` / `OnCookingDragMove(itemId, from, to, pos)` | 烹饪区移动入口（右键/拖拽）；内部先 TryPreSplitForCooking，再移动返回的实例，并 TrackCookingBagTransition 登记（取消时 TryReturnCookingIngredientToBag 原生返还） |
| `OnMoveItem(fromOwnerId, itemId, toOwnerId, bagPos)` | 参数序已确证；曾用于旧拆分方案（已废弃） |
| `AddItem(owner,…)` | 对"无网格配置的 owner"抛 KeyNotFound；对地面虚拟 owner 会写脏数据 |
| `RemoveItem(instanceId)` | 对**原生创建**的物品安全；对克隆对象崩溃（所以禁止克隆）。1 参/2 参两个重载，Harmony 补丁必须显式指定参数类型 |
| `GetItemDataList(owner)` | 会驱逐 count=0 脏条目并 LogError（游戏自检器） |
| `OwnerCache` | 混有地面掉落等虚拟 owner，**无法可靠区分**（旧中转方案翻车的根因） |
| WebUIVm.HandleCallback(ev, json) | JS→C# 事件总入口；事件名如 CLICK_ITEM / ITEM_CLICK（工作台）/ SORT_BAG |
| 工作台点击 | 左栏物品 = ITEM_CLICK（带 rightClick 字段）；配方点击 = ACTION_RECIPE_CLICK（信封 json：{action,id,data}） |
| 无人机交易界面 | TradeUI.html：CLICK_ITEM 用 `"itemKey":"123"`（带引号字符串，非 itemId）；官方语义 = 右键/Shift+点击 快速转移，普通点击 = 查看详情。物品 ID 正则必须兼容 itemKey + 引号（v2.9.21） |
| 快照型 WebUI 刷新 | TradeUI/烹饪等界面不消费 LogicAdapter 增量通知，吃 State.BagItemsJson 全量快照；TradeUI 的列表只在 ApplyTab（切换页签）时整体重建、新条目永不追加，SwitchBag 同容器有官方短路，GetData&lt;T&gt; 泛型与泛型 List 补丁参数均不可用（v2.9.22~27 四轮实证）→ **无人机交易界面划为官方行为区**：整理放行原版、不做拆分；烹饪界面用 `Ac_Cooking_RefreshBag.SendAction()`（v2.9.28 定稿） |

### 物品分类与官方行为（v2.9.20 确证）

| 类别 | 判定 | 官方行为 | mod 策略 |
|---|---|---|---|
| 多次使用物品 | `ItemData.MaxUseTimes > 1`（看上限，不看剩余） | 烹饪预拆分"1 次使用"进烹饪区，一次消耗 1 次使用 | **不改写 StackLimit、不合并**，100% 官方 |
| 单次使用物品 | `MaxUseTimes == 1`（如梳打饼干/卤蛋） | 可堆叠路径按数量消耗（1 份=1 次使用） | 照常堆叠 999、可合并 |
| 普通物资 | 无使用次数 | 可堆叠路径按数量消耗 | 照常堆叠 999 |

## 游戏更新后的兼容性检查（v2.9.28 增补）

1. **小更新/内容补丁**：什么都不用做。首启 BepInEx 自动重建 interop（启动慢 1~2 分钟属正常），mod 原地继续工作；玩出问题再排查。
2. **大更新/怀疑不兼容**：两步验证（约 1 分钟）——
   ① Il2CppDumper 解析新 GameAssembly.dll + global-metadata.dat，比对依赖清单（工具链见 03-教训与红线）；
   ② 用新 interop 重新编译 mod：0 错误 = 全部引用的 API 签名仍存在，可直接玩。
3. **需要改代码才重新部署**的只有一种情况：第 ② 步编译报缺 API（游戏重命名/删除了依赖成员）。
4. 字段偏移（StackLimit 0x5C / Burden）运行时动态读取，更新后自动适配，无需处理。
